# Architecture

Правила разработки по первым двум урокам Simple Architecture.

## View

- Компонент (View) содержит JSX и вызов своего хука `usePresenter`.
  Если собственной логики нет, пустой Presenter не нужен.
- View не содержит и не импортирует JS-логику, кроме `usePresenter`.
  Импорты дочерних компонентов, стилей и типов относятся к View.

## Presenter

- Обслуживает интерфейс: хранит его локальное состояние, выполняет эффекты,
  подготавливает данные и связывает события View с tasks.
- Порядок бизнес-действий, запросы и проверки сценария оставляй в task.
  Навигацию выполняй в Presenter: task не вызывает роутер и не принимает callback перехода.
- Усложняющийся Presenter разделяй на осмысленные хуки и функции.

## Tasks и сторы

- Task — обычная JS/TS-функция, реализующая сценарий пользователя (Interactor / use case).
  Определи её входные данные, результат и порядок действий. Называй глаголом:
  `logout`, `buyProduct`. Снаружи это один вызов; внутри допустимы помощники и другие tasks.
- Не используй в tasks React, JSX, хуки и React-привязки стора.
- Читай и обновляй стор напрямую через его API вне React.
- Данные сущностей и методы их обновления остаются в выбранном сторе (Entity).
  Детали запросов при необходимости скрывай за небольшими API-функциями.

## Структура файлов

- Каждый компонент имеет свою папку: View и стили — в ней,
  все хуки, включая `usePresenter`, и помощники Presenter — в её `logic`.
- Локальные tasks размещай в `logic/tasks` компонента. Task может быть файлом
  или папкой с несколькими файлами. Создавай папки при наличии соответствующей логики.
- Если компонент используется только одним родительским компонентом,
  размещай его папку внутри папки этого родителя. Повторяй правило для дочерних
  компонентов: дерево папок должно отражать структуру интерфейса.
- В `components` храни только переиспользуемые компоненты.
  Все их родительские компоненты должны находиться в поддереве родителя этой папки.
  Например, `MessageList/components/Reply` доступен только внутри `MessageList`.
- Используй глобальную `components` для общего переиспользования;
  вложенные `components` создавай при необходимости ограничить его ветвью.
  При появлении родительского компонента вне ветви пересмотри размещение компонента.
- Переиспользуемые tasks размещай в общей папке `tasks` с той же областью
  переиспользования, что и у `components`; глобальная `tasks` — для общего использования.
- Не более 120 строк в файле с кодом. Обеспечивай лимит правилом ESLint
  `max-lines` с максимумом `120`, сохраняя принятый способ учёта пустых строк
  и комментариев. Разделяй код по ответственности, а не уплотняй форматирование.

## Применение

- Найди компонент и его родительские компоненты; соблюдай принятые имена файлов,
  типизацию, систему стилей и используемые библиотеки.
- Не вводи дополнительных ограничений на выражения внутри JSX, props/children и типизацию.
- При рефакторинге сохраняй поведение и порядок действий. Не расширяй задачу
  до миграции приложения и не достраивай правила зависимостей или слои будущих уроков.
- Проверь размер изменённых файлов, наличие правила `max-lines`
  и доступные проверки проекта. При ревью указывай конкретные нарушения.
- Решения, не описанные здесь, обозначай как отдельные решения проекта;
  существенную неоднозначность уточняй.
