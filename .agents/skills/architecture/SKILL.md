# Architecture

Разделяй представление и логику, декомпозируй файлы и организуй дерево
React-компонентов по следующим правилам.

## View и Presenter

- Каждый React-компонент — view-слой: JSX и вызов своего хука `usePresenter`.
- Model предоставляет данные, View отображает их, Presenter получает данные
  из Model и подготавливает их для отображения.
- Вынеси всю JS-логику компонента в presenter-слой: состояние, эффекты,
  получение и преобразование данных, обработчики событий, валидацию.
- View не содержит и не импортирует JS-логику, кроме `usePresenter`.
  Не вызывай в нём другие хуки и не подключай напрямую API, хранилища
  или функции обработки данных. Дочерние компоненты и стили относятся к View.
- `usePresenter` возвращает всё, что нужно JSX: подготовленные данные
  и обработчики. View использует их для отображения и привязки событий.
- При усложнении Presenter выделяй осмысленные вспомогательные хуки
  и функции в отдельные файлы. Например, загрузку вариантов автодополнения
  можно вынести в `useSuggestions`, а проверку данных — в функцию валидации.
  Не задавай фиксированное число хуков или абстракций.

## Размер файлов

- Не более 120 строк в файле с кодом, включая View, Presenter и вспомогательные файлы.
- Обеспечивай ограничение правилом ESLint `max-lines` с максимумом `120`.
  При разработке проверяй его наличие; при ревью отмечай отсутствие.
  Сохраняй принятый в проекте способ учёта пустых строк и комментариев.
- Разделяй файлы по ответственности: части интерфейса — на компоненты,
  логику — на хуки и функции. Сокращение форматирования не заменяет декомпозицию.

## Дерево компонентов

- Один компонент — одна собственная папка с его View и Presenter.
  Стили и вспомогательная логика компонента располагаются рядом.
- Если у компонента один потребитель, помещай его папку непосредственно
  в папку этого потребителя. Повторяй правило для его дочерних компонентов.
- Файловое дерево должно отражать структуру интерфейса: к нужной части экрана
  можно пройти от родительского компонента к дочерним.
- Папка `components` содержит только переиспользуемые компоненты.
  Не складывай туда дочерние компоненты с единственным потребителем.
- Потребители компонентов из `components` находятся в поддереве её родителя.
  Не используй локальный переиспользуемый компонент из соседней или верхней ветви.
  При расширении области использования пересмотри его размещение.
- Для общих компонентов, например Input или Modal, подходит глобальная
  `components`. При необходимости создавай `components` внутри отдельной ветви
  для повторного использования только в ней. Вложенные `components` необязательны:
  если глобальной папки достаточно, не создавай дополнительные уровни.

Пример размещения: TextMessage и VoiceMessage используют общий Reply;
каждый из трёх компонентов находится в своей папке со своими View и Presenter.

```text
MessageList/
├── MessageList.tsx
├── usePresenter.ts
├── TextMessage/
│   ├── TextMessage.tsx
│   └── usePresenter.ts
├── VoiceMessage/
│   ├── VoiceMessage.tsx
│   └── usePresenter.ts
└── components/
    └── Reply/
        ├── Reply.tsx
        └── usePresenter.ts
```

## Что остаётся выбором проекта

- View может называться `index.jsx` или именем компонента; для TypeScript
  используй соответствующее расширение. Следуй принятому в проекте варианту.
- Сохраняй принятую в проекте систему стилей и используемые библиотеки.
- Не вводи дополнительных ограничений на выражения внутри JSX, props/children
  и типизацию. Не требуй пустой Presenter у компонента без собственной логики.

## Применение к задаче

1. Найди компонент, его потребителей и принятые имена файлов.
   Определи область изменения по запросу пользователя.
2. Раздели JSX и логику, сохранив существующее поведение при рефакторинге.
   Размести дочерние и переиспользуемые компоненты по правилам дерева.
3. Проверь размер изменённых файлов и доступные проверки проекта.
   При ревью сообщи конкретные нарушения и нужные изменения.
4. Не расширяй задачу до миграции всего приложения или добавления новых слоёв.
   Если решение требует правила, не описанного в этом скилле,
   обозначь это как отдельное решение проекта; существенную неоднозначность уточни.
